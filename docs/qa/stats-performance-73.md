## Итоговая схема

Все пять блоков используют `lazy: true`: переход на страницу не ждёт ответов,
каждый блок показывает собственное состояние загрузки/ошибки/данных.
Убран дополнительный watch лимита: обновление уже обеспечивает реактивный query.

API запускает фоновый обработчик вместе с lifespan. Он проверяет группы вопросов
через 15 секунд после предыдущего обхода. По изменившимся группам вычисляются
только отсутствующие эмбеддинги (существующий PostgreSQL-кеш векторов), затем
обновляется готовая группировка. При совпавшем отпечатке истории вычислений нет.
Это фоновый опрос, а не синхронная часть ответа бота и не обработчик открытия
страницы. При холодной истории готовность может занять время самой группировки.

Готовый снимок хранится в Redis и переживает перезапуск API. Его TTL 24 часа
продлевается фоновым обработчиком; при ошибке сохраняется предыдущий результат.
Отдельный namespace вычисляется из идентичности БД/инстанса с HMAC, секреты не
попадают в имена ключей. Ревизия настроек, объём выборки и порог сходства
разделяют снимки. Lease Redis исключает дублирование фоновой работы несколькими
API workers; долгий поток дожидается завершения до освобождения lease.

`GET /logs/popular` **не выполняет агрегацию SQL, эмбеддинги и кластеризацию**.
Он только читает снимок и отдаёт `status: pending | ready | error`, `updated_at`
и нужное число вопросов. Готовый снимок доступен независимо от визитов на сайт.
Редкие нестандартные raw_limit/threshold регистрируются для следующего фонового
обхода, число активных конфигураций ограничено 16; стандартная закреплена.

Фронтенд показывает подготовку отдельно от пустой истории. Пока снимок ещё
готовится или первая подготовка завершилась ошибкой, видимая вкладка раз в две
секунды читает статус. После готовности и при уходе со страницы опрос прекращается.
Старый backend без поля status поддерживается; прочие блоки не ждут этот снимок.

## Проверки

- До lazy-loading тест с удержанным popular GET падал: заголовок статистики
  не появлялся. После исправления доступны страница, готовые пользователи и
  независимый индикатор вопросов.
- Проверяются один GET при смене лимита, переход pending → ready и отдельное
  состояние ошибки подготовки без ложного «Нет данных».
- Backend-тесты используют отдельную настоящую PostgreSQL-базу и fakeredis:
  подготовка без визитов, новые вопросы, отсутствие пересчёта неизменной истории,
  сохранение после перезапуска, общая lease, TTL, настройки, разные namespaces,
  сохранение старого снимка при ошибке, удержание lease до окончания потока.
- HTTP-регрессия запрещает открывать БД/вызывать модели при запросе ещё не
  подготовленного снимка. Ожидается быстрый pending, а не вычисление в GET.

После выкладки требуется повторить HTTP-замер на СИБГИУ. Цель для prepared GET
на том же loopback — менее 0,5 с; отсутствие вычислений при GET проверяется также
автоматически. Полный E2E выполняется в CI.
