## Изменения

Все пять блоков используют `lazy: true`: переход на страницу не ждёт ответов,
каждый блок показывает собственное состояние загрузки/ошибки/данных. Число
запросов при открытии осталось равным пяти. Удалён дополнительный `watch`
на лимит вопросов: обновление уже обеспечивает реактивный query.

Связанный backend PR кеширует готовый список кластеров на 300 секунд:
16 LRU-записей на процесс API, общий результат для разных отображаемых лимитов,
отдельные ключи для объёма выборки, порога сходства и ревизии настроек.
Одновременные обычные промахи по одному ключу выполняют один расчёт.
Кластеризация перенесена в поток, чтобы не занимать event loop.
Каждый стенд запускает отдельный процесс API: межвузовского общего кеша нет.

## Проверка кеша на том же наборе

Новый сервис запущен отдельным временным процессом в контейнере СИБГИУ,
без изменения запущенного API или настроек. Прочитаны существующие векторы;
заглушка запрещала новые обращения к провайдеру.

- Холодный результат: 19.053630 с.
- Повторное чтение готового результата: 0.000143 с и 0.000083 с.

Это время метода сервиса, **не HTTP и не загрузка страницы в браузере**.
После выкладки следует отдельно повторить HTTP-замеры.
Счётчики популярных вопросов могут отставать на пять минут. После перезапуска
процесса или истечения TTL первый запрос снова выполняет холодный расчёт,
но не блокирует остальные блоки страницы. Кеш в памяти, не общий для нескольких
API workers. Ошибки расчёта в кеш не записываются.

## Регрессии

`tests/e2e/stats-loading.spec.ts` удерживает запрос популярных вопросов:
до исправления заголовок статистики не появляется (тест падает), после — видны
заголовок, 17 новых пользователей и независимый индикатор популярных вопросов.
Другой тест проверяет один GET при смене лимита.
Backend-тесты работают с реальной отдельной PostgreSQL-базой: повторный hit,
разные лимиты, четыре одновременных промаха, TTL, ревизия настроек, повтор после
ошибки, разделение ключей и вытеснение LRU.
