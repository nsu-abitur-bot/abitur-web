# Техническая совместимость одобренного интерфейса

**Итог: условно да.** Визуальную систему можно перенести в Nuxt 4/Vue/Nuxt UI поверх существующего API, сохранив действующие страницы. Большинство разрывов закрывается frontend-адаптерами; буквальное подключение HTML даст неверные статусы, неполные настройки и потерю операций. Production/deployed server не проверен: доступа нет; это аудит кода и исполнимых контрактов, без вызова провайдеров, БД, мутаций, тестов или запуска оценки.

Срез: backend `feat/instance-settings-356`, HEAD `3aff62b` (ветка работы PR360); frontend той же ветки HEAD `9a9fce6`; локальный backend `main` — `8eac5d1`. Main не содержит `api/routes/instance_settings.py`, `config/instance.py`, runtime watcher: подключения зависят от доставки ветки, их наличие на сервере не подтверждено. Сравнение с локальным main не означает сравнения с последним remote main. Источники: текущие `/tmp/abitur-admin-symposium/prototype.html` (разметка 20–40, fixtures 44–45, обработчики 47–56, shell 61–63) и `ui-system/ui-refined.css:5` (токены), реальные routes/services/schemas/dependencies/catalog. Старые ux-audit/ui-proposal не использовались как источник контрактов.

Обозначения: **ready** — серверный контракт достаточен; **frontend-adapter** — нужен код связывания/преобразования; **backend-gap** — точных данных/поведения нет; **intentional-demo** — сценарий/fixture надо удалить из рабочего интерфейса. Все endpoint ниже имеют префикс `/api/v1`. A = admin/superadmin, S = superadmin, V = любой активный авторизованный, включая viewer. Пути backend относительно рабочего каталога, frontend относительно `/Users/marat/projects/abitur/abitur-web`.

### Точное отображение единой колонки состояния

`GET docs.status` — **Document.status**, не status LightRAG: `rag.py:340`; `DocumentService.save_check_results`, `db/postgres/services/document.py:226`, перезаписывает его результатом freshness. `create_or_update_for_source:109` ставит «проиндексирован» и дату **до завершения ingestion**. Поэтому status и last_indexed_at сами по себе не доказательство наличия embeddings/успешной обработки.

| Реальные данные                             | Честная подпись / фильтр                                                                                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| diagnostics.lightrag_status=processed       | «Обработан» только как статус LightRAG; не «источник актуален». Это не гарантия качества поиска; entities=0 и chunks_count показывать в диагностике   |
| pending / processing                        | «Ожидает обработки» / «Обрабатывается»; attention, без %/ETA                                                                                          |
| failed                                      | «Ошибка обработки» + diagnostics.error; attention                                                                                                     |
| not_found / unknown / diagnostics GET error | «Обработка не подтверждена»; attention или отдельное unknown; сетевой сбой не равен failed                                                            |
| PG changed / изменён                        | Главное «Источник изменился», вторично реальное состояние LightRAG; attention даже при processed                                                      |
| source_unavailable / источник недоступен    | «Не удалось проверить источник» + last_check_message; attention, старый индекс может сохраниться                                                      |
| no_source / нет ссылки                      | «Нет ссылки для проверки»; это нормально для локального текста/файла, не ошибка обработки. В ready при подтвержденном processed, пояснение в карточке |
| indexing_failed / ошибка индексации         | «Ошибка индексации»; attention даже если другие данные еще старые                                                                                     |
| indexed / проиндексирован / active          | Это запись PG, не отдельный process. Для «Обработаны» требуется diagnostics processed; last_checked_at=null → «Источник не проверялся»                |
| check result «без изменений» / «обновлён»   | Временный результат операции; save_check_results преобразует в PG «проиндексирован». Проверка «без изменений» не лечит failed LightRAG                |

Минимально корректный ready = подтвержденный processed без changed/source_unavailable/indexing_failed; no_source — отдельная нейтральная пометка. Attention = остальные проблемы/неподтвержденная обработка. Для точного фильтра всего списка нужны diagnostics **всех** документов (ограниченная параллельность, cache); lazy diagnostics только открытой карточки не может дать точный ready count. Без массовых GET назвать фильтр «Без замечаний в реестре» и не обещать обработанность, либо добавить на backend агрегированные `processing_status`/freshness поля списка (предпочтительное небольшое расширение, не условие первого read-only этапа). Не копировать fixture d.process.

Особые ограничения: hash сравнивает сырые байты URL, а не смысл текста/актуальность правил; у file ingestion source_url извлекается из **содержимого** (`rag_upload.py:152`), так что URL может не быть адресом самого файла. При подтверждении URL hash может быть от fetch, а при его ошибке — от текста (`rag.py:259`), будущая проверка даст изменение. Обновление удаляет старый RAG doc **до** add_texts (`document_update.py:145`): не обещать rollback или неизменную доступность старого содержимого при ошибке.

## Обязательное и первый безопасный этап

**До включения реальных записей обязательно:** согласовать status mapping и честные подписи неизвестного типа; сохранить весь settings catalog и корректный changes/revision/secret flow; исправить RAG-only формулировку и deep-link URL mapping; подключить реальную eval shape без старых fallback; дать per-item результаты bulk операций; сохранить все текущие операции/маршруты через старые компоненты/дополнительное меню. Это не требует переработки архитектуры сервера. Точный MIME, batch diagnostics endpoint, RAG source IDs, живой model catalog, full-pipeline preview и runtime acknowledgments — дополнительные backend улучшения; первые три можно временно обойти честным unknown/URL mapping/ограниченными diagnostics GET.

Первый этап: перенести визуальные tokens и shell в отдельную Nuxt preview route/feature flag, оставив текущие страницы доступными; включить только GET docs/content/diagnostics и GET settings для S, остальные кнопки пока явно недоступны. Показать состояния loading/empty/error/403/404/unknown на адаптерах, не fixtures; сохранить dark mode/публичный rating/login и корректные role guards. Затем на изолированной QA среде проверить контрактные сценарии частичных ошибок, 409/rebase и секретов, после этого отдельно подключать существующие mutation endpoints (URL parse и инспектор тоже могут вызывать провайдеров) и eval с явным действием администратора. Для релиза сверить фактически установленную backend версию и конфигурацию сервера; данный аудит этого не подтверждает и PR/реализацию не создает.
