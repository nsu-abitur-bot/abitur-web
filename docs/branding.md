# Оформление вуза

Связанный контракт и тома: backend `docs/branding.md`, задача
https://github.com/nsu-abitur-bot/abitur-web/issues/45.

Выкладывать API с публичным `GET /api/v1/branding` и media endpoint первым,
затем frontend. Старые authenticated university/profile и instance settings
сохраняются. Новый UI до авторизации запрашивает только whitelist бренда,
без cookie/Authorization и без контактов или конфигурации провайдеров.

Один логотип, названия и HEX-цвет редактируются в Подключения → Оформление вуза.
Сайт, контакты и ASSISTANT_NAME сохраняются API, но исключены из формы и шапки.
Технический профиль находится отдельно; профиль не является переключателем темы.

`UNIVERSITY_ACCENT_COLOR` — единственный цвет. Палитра вычисляется локально:
светлый текст на тёмном акценте светлой темы, тёмный на светлом акценте тёмной.
Семантические success/error/warning не меняются. Переменные Nuxt UI и админки
получают одну палитру; preview имеет собственную область CSS-переменных.
Изменения черновика не затрагивают сохранённое оформление, включая head icon.

Файл и все изменённые поля сохраняются одним multipart запросом с revision.
Без загрузки/удаления используется совместимый PUT настроек. При 409 черновик
и выбранный файл остаются; загрузка новой версии переносит только локальные
правки и отмечает пересечения. При ошибке можно повторить, отмена загружает
актуальную версию. После неоднозначного сетевого обрыва стоит загрузить версию:
запрос мог сохраниться на сервере до потери ответа.

Media URL разрешается относительно NUXT_PUBLIC_API_BASE_URL через URL API,
без browser-only window/location, поэтому работает и в SSR. HTTP(S) legacy
логотипы поддерживаются. Невалидный URL/ошибка изображения дают букву; отсутствие
или ошибка подготовленной иконки — `/favicon.svg` проекта. Статическая ссылка
есть в HTML, включая login; после публичного запроса заменяется подготовленной
иконкой. UUID URL меняется при каждой загрузке, удаление возвращает fallback.
Отдельного поля/термина favicon в форме нет.

Настройка nsu.abitur.site после согласованной выкладки выполняется основным
агентом: официальный логотип и цвет НГУ из официального источника, названия,
проверка preview и Save. Затем login/reload, навигация, вкладка, темы и mobile.
Настройки моделей/ботов не менять, MAX не включать. Данные и media-том сохранить.
VPS этой задачей не изменяется.

## Воспроизводимая QA с реальным API

`tests/qa/branding-real.mjs` — отдельный opt-in сценарий Chromium, запускаемый
через Node с установленными зависимостями. Он принимает только loopback API/web
(по умолчанию 56546/56547), требует специально созданного QA superadmin
`branding-qa` с тестовым паролем из сценария и отдельной тестовой БД. Никогда
не запускайте его против рабочего экземпляра. QA-исходники логотипов
`/tmp/abitur-branding-45/logo.png` и `replacement.png` синтетические, не бренд НГУ.
Отчёт/head/resource evidence и screenshots сохраняются в эту же папку.

Обычный `task e2e` остаётся изолированным от настоящих API и ключей;
фикстуры обновлены под публичный endpoint. Для проверки реального API сначала
поднять собственный PostgreSQL/схему и API с PYTHON_DOTENV_DISABLED=1, отдельными
media/data/log directories и фиктивным SECRET_KEY. После QA остановить сервисы.
